## 已核实的接口事实

当前引擎类型：`/tmp/claude-1000/bundled-skills/2.1.319/d750a89a3652619196558ff6582348c3/plugin-authoring/types/claude-code.d.ts`。

- `session.append` 给出稳定 uuid、agentId、来源；`next` 返回实际保存消息；会话恢复加载不会重新触发 append。参考类型 11454–11599、reference.md 173–179。
- `session.messages` 最多返回 4096 条；不能据此宣称完整历史覆盖。参考类型 2862–2895。
- `session.compact` 支持 auto/manual/plugin/precompute，保留消息的 handle 指向引擎原件。参考类型 11648–11763。
- `$.session.compact()` 在运行中的 turn 会拒绝执行；不能在模型工具处理函数中直接实施 new_context。参考类型 2991–3002。
- `turn.step` 只支持修改 model/effort，不能修改请求消息。参考类型 14799–14846。
- `$.store` 是插件级 JSON 存储，总容量上限 4 MiB；`$.fs.read` 单次上限 4 MiB。完整历史需要独立持久化存储。参考类型 3392–3418、3513–3543。
- `prompt.context` 自定义块在初始请求与压缩后缺少副本时注入一次；动态状态不能假定每次调用都会替换原块。参考类型 8969–9011。
- `$.tool.register` 从下一次 prompt 起提供工具，因此工具需在 session.start 注册。参考类型 3200–3216。
- 当前 Jev recap 约 120 词，用于后续消息分类；包含 GOAL/NOW/LAST AGENT MESSAGE/PERSON'S STANDING INSTRUCTIONS。来源 `mods/jev/src/recap.ts:34`。

## 设计约束

- 保留原始消息和权限来源；工具结果不能通过摘要变成用户授权。
- 继续任务必须保留当前目标、最新用户修正、未完成状态和证据引用。
- 历史只读查询不重新执行工具，也不把旧协议块拼回活动会话。

## 主会话第一轮提案

目标：压缩后持续掌握当前任务，并能用稳定引用恢复已经离开活动上下文的证据。

三个组成部分：

1. 本地历史索引：按会话、agent、分支、消息 uuid 和内容版本保存原文与来源；查询返回带来源的文本片段。持久化原始会话是恢复依据，append 事件支持实时增量；恢复加载及引擎后续修改需要对账。
2. 任务交接记录：用户请求和限制保留原文引用；执行事实来自工具结果；解释和任务状态属于模型判断，不能据此声称语义正确性得到程序证明。
3. 压缩恢复：使用引擎原生压缩维护协议结构；压缩前准备覆盖位置明确的交接记录；压缩后把交接记录与查询入口送入模型上下文。

正确性目标：历史引用必须可解析、来源和分支必须匹配、压缩前后的未覆盖增量必须被识别。模型是否完整理解所有用户意图和是否选择了正确的历史查询仍需真实任务验证。

独立核实的实现方向：用本地 SQLite 保存全文索引及交接版本，由随 mod 分发的本地辅助程序读写；`$.process.run` 接收 argv 与 stdin，提供 exitCode 和输出截断标志。写入在事务中完成，失败显式报错；`$.store` 不承载整份历史。查询分页返回，避免通过标准输出一次装载全会话。当前仅为设计，不安装依赖、不创建数据库。

## 需要在讨论中解决的具体场景

- 后台整理已覆盖某条回复，用户紧接着更改目标；压缩必须处理这条修正，不能安装过期交接内容。
- 测试曾通过，随后代码又被修改；历史应记录该次检查通过，不能自动推断现在代码通过检查。
- 同一个项目存在主会话、子 agent、fork 和回退分支；历史搜索必须遵循当前分支的可见范围。
- 进程在记录交接状态、原生压缩、注入恢复内容的任一位置终止；恢复后必须依据实际会话边界判断是否切换完成。
- 插件晚加载、历史超过4096条、工具结果被截断、文件含多模态引用；覆盖缺口必须明确，不能制造完整历史承诺。
- 历史检索不断产生新工具结果；查询应有分页和输出预算，同一上下文内避免反复返回同一版本同一区间。
- 查询工具自己返回的历史摘录再次被记录时，保存来源引用，搜索优先命中原始消息，避免把摘录副本当新事实反复总结。

## 主会话第二轮审查重点

- 分开记录动作与任务解释：命令执行结果是事实，任务完成度是带证据的判断。后续修改不改写旧检查结果，也不把旧结果自动适用到新文件状态。
- 候选交接记录包含 coveredThrough、分支版本、来源引用。晚到的结果只能覆盖它确实处理过的前缀，不能标记之后的用户消息已经处理。
- 对压缩后的首次请求是否确实包含恢复块，不用“已写入数据库”代替验证；候选生成、原生压缩完成、恢复块送入模型是三个不同状态。
- 当前会话转录文件的字段检查证实存在 user/assistant/attachment/system 及请求跟踪等多种记录，没有实际 compact_boundary 样本；不能据此声称已经验证了边界字段格式或调用时序。

## 第一轮讨论结果

审阅者同意三个分工：存原文、引擎压缩、恢复当前任务记录；提出三种具体失败：同一轮内压缩时恢复内容插入顺序、resume/fork 分支关联、用户修改要求时旧约束残留。

主会话的决定：

- 只对当前任务做上下文连续性；不加入跨项目长期记忆。
- 完整历史索引读取项目转录文件，`~/.claude/history.jsonl` 仅帮助定位输入历史；本机前20条记录只有 display/pastedContents/project/timestamp 等字段，没有工具结果和助手消息全文。
- 原生压缩输出不由插件手工重建。历史查询返回引用文本，不重放旧 tool_use / server_tool_use。
- 对“追加接口绝不会造成重复”的主张不作保证；接口类型只证明可用能力，恢复路径与消息顺序需要实际验证。
- 提出 `prompt.context` 注入恢复块，交第二轮审阅，以避免在追加回调里再次追加而形成顺序或重入问题。
- Jev 继续使用自己的任务分类 recap；新模块提供完整交接状态，暂不改变 Jev 的模型、时机或分类逻辑，防止扩大本次设计范围。

第一轮审阅只读源码，未运行验证。主会话另核实旧修复程序 `/home/ubuntu/sipeng/scratch/jev_repair/repair_all.py:28`：其查找当前链同时考虑 parentUuid 与 logicalParentUuid；索引设计需要记录分支归属，不能把转录文件中的所有记录一概视作活动历史。

## 第二轮讨论结果

审阅者补充四个反例：恢复块在当前窗口内不会自动更新；多次压缩可能丢掉未再次提及的未完成事项；prompt.context 没有 agentId；分支回退不会撤销文件、远端服务和后台进程的实际变化。

达成的设计要求：

- 交接记录明确标注截至位置，此后消息继续更新任务；不能将旧状态当作当前物理世界。
- 未完成事项从上一代继承，每次关闭必须附来源；新交接不能只总结最近增量。
- 历史查询按会话、agent、分支隔离。放弃分支上的动作可作为需要重新核实的历史事实，不能将其用户授权恢复到另一分支。
- 数据库偏移只在事务提交成功后更新；候选更新带版本检查，晚到的候选不能覆盖更新的记录。
- 查询入口给出当前任务的具体证据引用，以及尚未整理的区间；查询结果有分页和输出预算。

转入第三轮的反例：

- `e.messages` 没有 uuid，不能直接“取最后消息 uuid”，需要可靠的快照引用方式。
- `prompt.context` 的 agent 归属和调用顺序尚不能证明，不能承诺在所有loop首次压缩后请求前注入。
- 用户要求错误就停止；数据库/交接记录写入失败时，统一终止这次压缩，不采用“自动压缩失败就静默降级”的恢复策略。
- `SessionCompacted.messages` 合同明确允许原样保留引擎消息并增加新消息。第三轮需检查：追加一条全新纯文本交接消息能否让恢复内容与原生摘要一同安装，而不重建旧协议消息。
- 可以对冻结的 `e.messages` 产生独立归档快照，以 checkpointId + itemIndex 提供稳定引用；原始 handle 只活在本次 hook 中，不写入持久化数据库作为可重放消息身份。

## 第三轮审查中的简化判据

- 覆盖边界直接取本次冻结的压缩输入，并给快照分配独立引用；不按文本、消息条数或工具调用锚点猜测源 uuid。
- 比较“让摘要器照抄引用并逐字验收”与“由程序追加新纯文本交接消息”的机制风险：后者依据 SessionCompacted 的现有返回合同，可以保留原生返回的消息对象，同时让交接文本不依赖摘要器照抄。
- 纯文本交接消息必须不含旧 tool_use、tool_result、server_tool_use、thinking 或旧消息 id；原生返回的消息由引擎保持身份。此结构是否在 resume/subagent/同轮自动压缩中保持正确，仍须真实会话验证。
- 检查点和交接包先持久化，活动历史内出现的交接包引用作为采用依据。写入成功但未被会话采用的快照保留为未采用记录；不得因数据库有“最新版本”就向回退分支注入它。
- 原生 precompute 结果可能等待到后续历史变化后安装。若现有接口不能重新校验尾部，设计关闭该模式；后台任务记录整理仍可进行，实际压缩时必须绑定真实输入。

## 第三轮讨论结果与最终判断

审阅者接受压缩输入快照与独立引用，指出投影消息中的 user 角色也可能来自上一代摘要，必须核实来源；提出压缩后 append 恢复消息的方案，同时列明其安装后通知、下一次请求前送达、并发新消息保留三项运行条件。

主会话依据已读 `SessionCompacted` 合同作最终选择：保持 `next(e)` 返回的全部原生消息不变，只增加一条没有旧 ID、工具调用或思考块的全新纯文本交接消息，由引擎按最终返回集合安装。类型 11663–11672 明确描述了这类返回结果。采用该方式不依赖额外的“已安装后再追加”事件，也不要求摘要模型逐字照抄交接包。

两者的实质差异：安装后 append 存在两次独立状态变更之间的空隙；将新纯文本消息放入最终返回集合，把交接内容纳入同一安装动作。此结论是接口合同支持的设计判断，并非已完成运行验证。尤其必须检查原生结果的句柄保持、持久化身份、同轮自动压缩和子 agent 的真实行为。

最终约束：

- 归档引用精确指向本次输入快照；来源未判定的消息不能标成用户原话。
- 数据库或交接准备失败停止压缩；上下文不足时暂停任务并报告原因。
- 恢复根据活动历史内实际采用的 checkpointId；不能取数据库最新版本作为当前事实。
- 历史读取不重放协议块，检索摘录不作为新证据循环进入索引。
- 未完成事项跨代继承，当前状态遵循后续消息；外部进程和文件状态在动作前重新核实。
- 现有 API 支持机制的表达；能否满足消息身份、并发顺序和崩溃恢复不变量，要由真实会话验收决定，不预先宣称绝对不会丢失或重复。

三轮均为只读设计审查，没有运行模型评测、压缩试验或修改 mod 实现。

## 新增接口核实

- `$.process.run` 支持数组命令和 stdin，返回 exitCode、标准输出及截断标志；本地辅助程序可以按结构化请求增量读取大文件。类型 8410–8468。
- `classic.PostCompact` 输入包含 trigger（manual/auto）和 compact_summary，但类型本身没有证明它覆盖每一种插件触发或预计算安装路径；不能单靠它做通用提交确认。类型 8203–8209。
- `prompt.context` 可用于注入恢复块；必须在真实自动压缩、恢复加载、预计算复用路径上核实调用顺序。静态类型仅证明接口存在。
