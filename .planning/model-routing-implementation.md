# claude-magpie 任务与模型路由：实现方案

日期：2026-11-09。本文汇总已与用户确认的实现细节、由接口事实决定的做法，以及实现开始时需要先验证的接口行为。行为规则见[系统行为约定](model-routing-design.md)，模型与思考强度的分工见[模型路由表](model-routing-table.md)。尚未开始实现。

## 1. 启用范围

新建一个插件，暂名 `magpie-tasks`，与仓库中的其他插件一样经本地插件市场安装。会话启动时检查 API 地址：只有当 `ANTHROPIC_BASE_URL` 指向 Magpie 网关时，插件才注册钩子和工具；普通 `claude` 会话中它不做任何事。

采用自行判断的原因：`claude-magpie` 是 Magpie 生成的启动脚本（`exec magpie claude run "$@"`），在其中加入插件参数会被 Magpie 重新生成时覆盖。

`claude-telegram` 保留命令名称，内部改为通过 `claude-magpie` 启动，并继续加载 Telegram 通道和 `tg-router`。它在启动时设置环境变量 `MAGPIE_TASKS_ROLE=router`，插件据此把这个会话当作 Telegram Router，不进入长期任务流程。

## 2. 会话与角色

| 角色 | 来源 | 模型 | 思考强度 | 工作方式 |
| --- | --- | --- | --- | --- |
| 长期任务架构师 | 每个交互式 `claude-magpie` 窗口 | 第一条消息后推荐，用户确认 | JEV 逐条判断 | 登记任务、转为后台会话；工作目录是项目主目录，按插件给出的绝对路径阅读任务工作副本；读取材料、讨论设计、委派实施；直接修改项目文件由工具限制禁止 |
| Telegram Router | `claude-telegram` 主对话 | Opus 5.5 | JEV 逐条判断 | 判断消息归属、创建日常任务子代理、转交长期任务；沿用 `tg-router` 的工具限制 |
| 日常任务子代理 | Router 创建 | 按路由规则 | 规则强度；Jev 判断需要深入推理时加一级；验收失败或诊断后重新委派时再加一级 | 在独立工作副本中执行；成果值得独立检查时由验收子代理检查一次，随后自动整合 |
| 实施子代理 | 架构师委派 | 按路由规则 | 同上 | 独立上下文；在任务工作副本中修改与验证；同一任务续接原代理 |
| 评估、诊断子代理 | Router 或架构师 | `route-assessment` 等规则 | 同上 | 提供选模推荐或失败诊断及依据 |
| 验收子代理 | 日常任务的一轮完成、且 Jev 判断成果值得独立检查时由插件启动 | `review` 规则 | 同上 | 独立上下文；对这一轮的成果检查一次 |

普通 `claude` 会话不受这些规则影响，可用于临时的小操作。

## 3. 模型与思考强度

**模型由插件在启动子代理时设置。** `agent.spawn` 钩子按路由规则改写 `model`，并把 `cwd` 设为任务的工作副本。实测证明这条路径有效（见第 10 节）。

以下入口保留自身机制：

- 复制完整会话的 fork 继承父模型。普通实施任务不使用它；用户明确要求时才使用。
- Workflow 代理的启动内容不可改写，只能拒绝；其模型由脚本中的 `model` 决定。
- 技能的独立运行（例如 `/code-review`）不经过 `agent.spawn`，保持官方流程。

`subagent-opus` 在 Fable 或 Mythos 父会话下会把子代理改为 Opus。它需要在 `magpie-tasks` 生效的会话中让出决定权，以免两个插件同时改写模型。

**判断任务。** 插件启动子代理时，把完整的委派说明交给 OpenAI 上的 Jev（Decisions API，模型 `gpt-6-luna`），在同一次请求中问两件事：说明属于哪条路由规则（取得选项、置信度和各选项概率），以及任务是否需要深入推理。完整说明可能长达数千字，这一步只在启动时做一次。置信度不足按“没有匹配规则”处理：长期任务由架构师说明选择；日常任务由评估子代理推荐，用户确认后分派。Jev 不可用时，由固定的评估模型代为判断，记录中标明使用了替代判断。Jev 的服务地址写在插件配置中。

**Jev 的服务与上下文。** Jev 只使用 OpenAI 的 Decisions API（`gpt-6-luna`），JEV 与本插件都使用它，密钥使用专用的个人密钥（`~/.config/jev-opus/openai-jev.key`）。

每次提问时，Jev 的上下文都从 Claude Code 当前的上下文（`$.session.messages({ as: "api" })`，子代理加 `agentId`）重新整理，因此跟随 Claude Code 的压缩：

- 保留：压缩摘要（压缩过时）、触发新一轮的用户侧内容（用户输入、去掉标签元数据的 Telegram 正文、展开后的斜杠命令、后台任务完成通知）、每一轮 agent 的最终回答。子代理的对应内容是委派说明、之后的补充消息和每次交回的报告。
- 去掉：工具调用、工具输出、两次工具调用之间的中间文字、系统提醒和钩子注入的内容。
- 以消息列表发送（不拼成一段文字），按原顺序排列，当前消息在最后。

这份列表是 Claude Code 上下文的一部分，claude-magpie 的上下文上限是 872,000 token，Decisions API 实测接受约 920,000 token，所以不会超限。2026-11-09 实测：以消息列表发送时，追加新消息后前面部分由缓存读取（59,597 个 token 中 57,729 个），拼成一段文字时追加内容后完全不走缓存；Claude Code 压缩后的第一次提问不走缓存。耗时：5.4 万 token 0.45 秒，21.4 万 token 1.2 秒，42.2 万 token 3.2 秒。OpenAI 拒绝请求（例如达到速率限额）时，这次判断按 Jev 不可用处理。

JEV 随之修改：Jev 只用 OpenAI；上下文按上面的规则整理；删除截断（`mods/jev/src/router.ts:64-71`）、Haiku 滚动摘要（`mods/jev/src/recap.ts`）和“上一轮做了什么”一行；任务类型、深入推理与“上一轮是否做错”在同一次请求中提问；问题措辞不再说明前文可能缺失；实施时用已标注消息重新校准门槛并测量准确率。普通 `claude` 会话中由 JEV 管理的子代理也加入失败升级：子代理内同一检查在修改代码后再次失败、到回合结束仍失败时，它的下一次续接提高一级（与主对话的现有规则一致，现有实现只记录子代理的检查结果、不提高强度，见 `mods/jev/hooks/register.tsx:458`、`:675`）。架构师与 Router 只使用 JEV 已覆盖的模型（Opus 5.5、Astra、Sol 6.1），JEV 的模型覆盖范围不扩大。

**思考强度。** 架构师与 Router 的主对话由 JEV 逐条判断。子代理的强度由插件决定，在子代理的每次请求中通过 `turn.step` 设置：

- 起始强度是规则强度；Jev 判断需要深入推理时提高一级。
- 续接子代理时，插件用新消息重新问一次是否需要深入推理，强度不低于这个子代理当前的强度。
- 验收不通过、或诊断后重新委派同一任务时，提高一级。
- 最高 max；每次调整记录原因。

JEV 不处理插件管理的子代理：插件在委派说明中写入任务标记，JEV 遇到带标记的子代理时不改写强度。JEV 需要为此增加这一项判断。

采用这种分工的原因（2026-11-09 核查，见 `findings.md`）：JEV 的标注与校准只覆盖主对话；它只读子代理说明的前 2200 个字和后 800 个字（`mods/jev/src/router.ts:64`），最近 245 份子代理说明中有 70 份超过 3000 字；它的失败升级只对主对话生效（`mods/jev/hooks/register.tsx:458`、`:675`）；路由表中的 Sonnet 5.5、Haiku 5.5、Fable 5.1、Terra 6.1、Luna 6、Sol 6 不在它的处理范围内。Jev 对委派说明的“深入推理”判断同样没有校准，判断结果写入任务记录，在路由校准中用实际结果检验。

**指定模型。** `agent.spawn` 中的 `model` 来自发起委派的模型，插件据此区分两种情况：

- 委派说明写明选模理由（用户指定，或架构师依据具体证据调整）时，采用指定的模型，并在记录中标为指定或调整。
- 带有模型却没有理由时，拒绝这次启动，提示补充理由或交给规则选择。

**代理定义自带的模型。** `agent.spawn` 的 `model` 只包含委派时明确传入的模型（Claude Code 2.1.319 插件类型定义 `AgentSpawnInput.model`）。代理定义文件中写的模型，例如 `code-editor`、`code-reader`、`doc-researcher` 的 `model: opus`，不出现在这个字段里，也不算作指定模型。插件按路由规则为这些代理设置模型，所以它们定义中的模型在 claude-magpie 中不生效；普通 `claude` 会话中照旧使用。

`tg-router` 目前固定以 `WORKER_MODEL = 'opus'` 创建日常任务子代理（`mods/tg-router/hooks/register.ts:40`）。在 claude-magpie 中它改为不指定模型，交给路由规则；用户在消息中明确要求某个模型时，Router 按上面的方式写明理由。

**Magpie 的职责。** Magpie 负责账号、额度、供应商与故障转移。`claude-magpie` 的默认模型指向具体模型；Magpie 路由组的自动强度只支持 low 到 xhigh，因此不用它决定强度。

## 4. 长期任务窗口

1. 用户在终端（herdr 窗格）运行 `claude-magpie`，发出第一条消息。
2. 插件根据这条消息，从 JEV 覆盖的模型（Opus 5.5、Astra、Sol 6.1）中推荐架构师模型，说明依据和证据限制，等待用户确认。当前目录不是 Git 仓库时，同一次确认中说明将在这个目录建立 Git 仓库，并列出目录路径、文件数量和总大小。
3. 确认后，插件登记任务；需要时执行 `git init` 并提交一份基线快照（记录当前全部文件，作为工作副本的起点）；创建任务工作副本。插件不在当前会话里切换模型：交互式 `/model` 会把选定模型写入用户设置，claude-magpie 退出时再把它写进 Magpie 的启动设置，改变以后所有 claude-magpie 会话的默认模型（2026-11-09 实测）。插件丢弃这条消息，用 `claude-magpie --bg --model <选定模型> "<第一条消息>"` 启动一个后台会话作为架构师，并在消息末尾告诉架构师任务工作副本的绝对路径；随后结束前台会话。架构师会话始终在项目主目录运行，context-memory 的项目范围历史搜索按会话工作目录划分项目。
4. 窗口显示 `claude attach <会话 ID>`。关闭窗口只断开显示，`/stop` 才结束会话。之后可用 `claude attach` 重新打开，也可从 Telegram 联系。

以下会话不进入这个流程：

- 设置了 `MAGPIE_TASKS_ROLE=router` 的 Telegram Router 会话。
- 插件自己启动或恢复的后台架构师会话（新任务、日常任务转为长期任务、从 Telegram 恢复、中断后恢复）。环境变量传不进后台会话（后台会话的环境由常驻服务生成），所以插件启动前在登记表写入待认领记录（任务 ID、工作目录、第一条消息的散列），后台会话第一次提交消息时按 `CLAUDE_JOB_DIR`、工作目录和散列认领，并把自己的会话 ID 写回登记表。
- `claude-magpie -p` 等只运行一次的非交互调用（会话启动事件的 `isInteractive` 为 false）。

已有会话第一次通过 `claude-magpie` 恢复时，插件询问一次是否接管。确认后沿用原模型与对话历史，登记为长期任务，接入 Telegram，并启用架构师的工具限制。 接管后插件从 `turn.complete` 发出 `/bg` 把会话转入后台；转入后台会生成新的会话 ID，登记表随之更新。

架构师的写入范围（依据 context-memory 会话的结论，约定见 `~/.codex/AGENTS.md` 的 Project Records 一节）：

- 允许用 Edit/Write 写入项目主目录（不是任务工作副本）中的 `.planning/findings.md`、`CONTEXT.md`、`.planning/plan-*.md` 和 `.planning/*.html`；允许运行 html-plan 的打包命令和 `~/sipeng/plans/publish-plan`。插件把路径解析为绝对路径后再判断。
- 这些是设计记录，不进入构建。很多项目的 `.planning/` 被 git 忽略，工作副本中没有，整合时也带不回项目，所以只能由架构师在主目录写入。
- 子代理的发现写在报告里交给架构师，由架构师写进 `findings.md`；子代理不在工作副本中修改 `CONTEXT.md`，避免整合时与架构师的修改冲突。
- 任务进度只用 context-memory 的 `notes_write`，它是工具调用，始终放行；不建 progress 文件。

## 5. Telegram 与长期任务的连接

- **转交消息：** Router 用 `$.session.send({ to: { sessionId } })` 把消息送给登记的架构师会话。会话未运行时，先用 `claude-magpie --bg --resume <会话 ID>` 恢复，再转交。
- **带回回复：** 架构师会话中的插件在回合结束时，直接通过 Telegram Bot API 把回答发回，作为原消息的回复。机器人令牌从 Telegram 状态目录读取；发送消息与通道服务器的轮询互不冲突，`tg-router` 现在就与通道服务器同时使用同一令牌发送。Router 不运行时，长期任务的回复照常送达。
- **主动通知：** 需要用户决定时（关键设计变化、修改冲突、没有进展而暂停、中断后无法自动恢复），以及任务或明确成果完成时。普通进展不推送。
- **日常任务转为长期任务：** 原子代理说明原因，Router 与用户讨论；用户确认后创建后台架构师会话，交接任务记录、关键材料和进度，保留任务身份与 Telegram 消息关联。
- **没有匹配规则的日常任务：** 评估子代理推荐模型与思考强度，Router 发到 Telegram，用户回复确认后才创建执行者。

## 6. 任务登记与记录

多个会话（Router、各个架构师）会同时读写登记信息，因此每个任务一个记录文件，写入时加锁，状态变化追加到任务日志。记录内容：

- 任务身份、类型（日常或长期）、负责人会话或代理 ID、状态（运行、暂停、等待用户、完成）、工作副本路径、Telegram 消息关联。
- 每次选模：规则 ID 与版本、Jev 的规则判断及置信度、深入推理判断、模型、起始强度及每次调整的原因、选择理由、是否替代判断、用户确认内容。
- 被复核模型与复核模型、上下文来源。
- 同一阻碍的诊断次数与模型更换次数，跨代理累计。
- 交付成果、验证结果、验收子代理的结论、返工与失败原因、用户原话反馈、评分。

逐次请求的耗时、token、缓存与最终强度沿用 JEV 日志（按会话与代理 ID 关联）；Magpie 用量记录提供实际服务的模型与账号。

## 7. 工作副本与整合

- 同一项目中的每个独立任务使用自己的 Git worktree（工作副本）。建议的做法：创建时把用户当前未提交的修改带入副本作为起点，整合时只应用任务自身相对这个起点的改动，用户未提交的修改保持原样。
- 长期任务的实施子代理默认共用任务工作副本；架构师在主目录运行，委派和验收时按插件给出的副本绝对路径阅读子代理的修改与差异。插件通过 `tool.call` 记录每个子代理改过的文件；两个仍在运行的子代理改动同一个文件，或一方的修改让另一方的验证失败时，插件暂停后来的一方，在窗口和 Telegram 提醒用户，询问是否给它单独的工作副本。用户同意后它在单独副本中继续，完成后合入任务工作副本；不同意时它等待前一方完成。
- 日常任务的执行子代理每完成一轮，插件先让 Jev 判断这一轮的成果是否值得独立检查（它读到用户这一轮的话、执行者的回答、这一轮的工具调用次数和等待整合的改动统计）：对话式的回答、交还、一步完成的指令和一两行的机械修改不验收，有改动时直接整合。值得检查时按 `review` 规则启动一个验收子代理，检查一次：重新运行执行者报告的验证命令，对照用户的原始请求检查改动范围和结果。通过后整合；不通过时把验收意见交回执行者修复，修复后的回答直接结束任务，修复后的改动连同验收意见发到 Telegram，用户确认后整合。验收通过与整合都不通知用户：插件把结果写成一行说明，附在下一条发给执行者的消息后面。用户只在需要决定时收到消息（整合冲突、返工后的改动是否整合）。
- 长期任务在架构师验收后、日常任务在验收通过或判断不需要验收后，自动把任务自身的改动应用回项目。同一项目的整合排队进行。
- 与用户现有修改或其他任务冲突时，先报告并等待用户决定。
- 不做 Git 提交和推送，除非用户明确要求。后台会话默认的“完成后提交并推送”行为由插件写入的会话指令覆盖（官方文档说明用户的 Git 指令优先）。
- 日常任务完成后在 Telegram 报告改了什么、怎样验证。

## 8. 中断与恢复

`claude-magpie` 或 `claude-telegram` 启动时检查登记表：

- 仍在运行的会话直接重新关联。
- 恢复已停止的会话时使用不带其他参数的 `claude --bg --resume <完整会话 ID> "<消息>"`，沿用会话保存的启动参数和原会话 ID；带参数恢复（包括 `claude-magpie --bg --resume`）或恢复仍在运行的会话，都会另起一份副本。仍在运行的会话用 `$.session.send` 投递消息。
- 已中断且没有被用户暂停的任务，核对工作副本中的文件与执行状态后恢复。
- 等待用户确认的事项继续等待。
- 无法确定某项操作是否完成时，暂停受影响的部分并报告。

后台架构师会话与 context-memory 的配合：

- 恢复会话沿用原会话的转录和笔记；同一任务改开全新会话时读不到旧笔记，只能依靠 `findings.md` 和项目范围的历史搜索，因此插件恢复任务时始终使用 `--resume`。
- 写笔记的说明由 context-memory 追加在系统提示末尾；启动后台会话时不使用 `--system-prompt` 替换系统提示（`--append-system-prompt` 不受影响）。
- context-memory 更新后，旧会话的压缩会失败并要求 `/reload-plugins`；后台会话无人执行，插件在 context-memory 更新后重新恢复这些会话。
- 归档写入失败会让压缩作废，原因只出现在界面和调试日志中。插件检查后台会话调试日志中的“context-memory 归档失败”或“hook failed closed: context-memory”，发现时在 Telegram 报告。

## 9. 评分与校准

- **评分：** 每天最多邀请一次，从当天完成的任务中随机选一个，附在 Telegram 完成通知里。回复数字 1–5 即评分，不回复视为跳过。用户随时可以对任务的任意消息回复“评分 N”。
- **校准提醒：** 每两周检查一次。两周内同一条规则有至少 3 个任务出现同类问题（返工、需要诊断或换模型、评分不高于 2、用户说结果不合适），或替代模型至少 3 次完成了原模型没完成的工作，才在 Telegram 提醒并列出对应任务和调整建议。用户直接说出对某个模型的看法时，一次即可触发。
- **规则文件：** 运行时读取一份可解析的路由规则文件，记录版本号。校准讨论后由用户确认修改，每次选模都记录当时的规则版本。
