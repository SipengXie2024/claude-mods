# 模型路由设计讨论

## 目标

根据任务需求、模型测评和个人使用证据选择模型及思考强度，以任务完成质量为首要目标。质量相近时考虑等待时间与额度消耗。用户可以了解选择依据，并参与规则校准。

本文记录已经确定的任务与权限规则。模型与 effort 的具体建议见[模型路由表](model-routing-table.md)，实现细节见[实现方案](model-routing-implementation.md)；尚未开始实现。

## 任务与入口

### Telegram 日常任务

Telegram Router 判断消息属于哪个任务，创建新的任务子代理或把追问送给原负责人。日常任务允许一个子代理直接完成工作，保留任务上下文并接收后续补充。完成后由一个独立上下文的验收子代理检查一次成果，通过后整合到项目。

日常任务发展为需要持续讨论关键设计的工作时，即使目标仍属于原任务，也与用户讨论是否建立长期任务窗口及其架构师。用户确认架构师模型后，交接目标、已确认决定、关键材料和进度，更新负责人并保留原任务及其追问关联。尚未确认的关键设计等待决定，已经明确且不受影响的工作可以继续。

日常任务没有适用路由规则时，Router 安排独立评估者准备模型与 effort 的推荐及依据，用户确认后才创建实际执行者。本次选择及确认内容记录为例外，通用规则在用户参与的校准讨论中调整。

### 长期任务窗口

每个长期任务有自己的架构师。用户说明目标后，系统依据路由规则和已有证据推荐架构师模型，解释依据及证据限制，由用户确认。选定模型在该任务内保持稳定。

架构师负责理解目标、整体方案、关键细节设计、实施安排和验收判断。架构师可以直接阅读关键代码、文档、差异和原始证据；大范围调查、修改文件与运行验证交给子代理。

任务进入新的工作阶段、临时插入相关问题，都可以继续使用原架构师。出现独立目标时，建议创建单独的任务会话，携带必要背景，用户决定是否接受以及选择哪个模型。用户也可以要求继续留在当前会话。

### 两个入口共享任务

Telegram 可以联系已登记的长期任务架构师，并把答复带回 Telegram。明确的任务引用直接转交；归属有歧义时询问用户。同一任务在窗口和 Telegram 中使用同一个负责人及决策记录。

## 子代理的上下文与任务划分

子代理启动时接收明确的任务说明和必要材料。普通实施任务不继承主对话全文。同一任务的补充与修复继续交给原子代理；独立任务创建新的子代理。

委派按照能够独立验收的成果划分。例如，为 JEV 增加模型支持时：

- 研究子代理提交测评证据，包括来源、条件和适用限制。
- 架构师与用户确定思考强度策略。
- 实施子代理修改 JEV，完成测试及真实会话验证，并修复发现的问题。

实现及其验证保留在同一个任务上下文中。

## 关键细节与设计决定

架构师必须掌握足以作出设计与验收判断的关键细节。子代理的交接内容包括：

- 结论、原始依据及适用条件。
- 接口限制、依赖关系、失败原因和影响方案的发现。
- 实际修改、验证范围及结果。
- 未解决的问题和需要决定的事项。

架构师可以直接检查原始材料。影响后续工作的事实需要保存在任务记录中。

涉及任务目标、模块职责、对外行为、模型选择原则或验收条件的关键设计变更，由子代理提交证据和建议，架构师核实并与用户讨论，取得同意后实施。受影响的工作等待决定；不受影响的工作和局部实现选择可以继续。

## 模型选择

新建普通任务子代理时：

1. 架构师或任务入口提供目标、约束和验收条件。
2. Jev 读完整的任务说明，判断匹配的规则与是否需要深入推理。
3. 路由规则结合模型证据选择模型及思考强度。
4. 架构师掌握规则未考虑的具体证据时，可以说明理由，调整本次选择。

用户明确指定的模型优先。调整通用路由原则需要用户参与讨论。日常任务没有架构师时，Jev 与规则表负责适用规则内的默认选择；Router 负责分派与传递结果，评估者和诊断者分别提供例外选模与失败处理的技术建议。没有匹配规则的模型推荐等待用户确认。

明确要求使用不同模型复核时，选择过程接收被复核任务的具体模型标识，排除原模型后再从适合任务的候选中选择。别名或 effort 变化仍属于同一模型；没有符合条件的候选时，报告限制并等待用户决定。

每个新任务显示一次简短说明，包含模型、思考强度和选择理由。同一任务继续执行时不重复提示；更换模型时说明原因。完整理由与执行结果进入任务记录。

## 不可用与无进展的处理

### 模型不可用或额度耗尽

路由表中存在有证据支持、符合任务质量要求的替代模型时，可以告知用户后交接任务继续执行，保留任务记录和已确认的设计。

没有合适替代模型时，用户决定等待或接受其他模型。

### 实施没有进展

同一阻碍持续存在，且尝试没有获得有效的新证据、缩小原因范围或改善验证结果时，需要介入判断。失败次数本身不足以确定这一状态。

长期任务由架构师介入。日常任务没有架构师时，由 Router 安排独立诊断子代理检查任务要求和失败证据，提出继续原代理、更换实施模型或交回用户决定的建议。建议符合既定目标、验收条件与已有选模规则时，Router 可以说明理由后自动分派；超出规则的选模建议、关键设计变化或缺少合适方案时，等待用户决定。

同一个无进展问题最多一次独立诊断，加一次实施模型更换；次数随任务记录保存，更换代理后继续累计。之后仍没有可验证的进展，则暂停受影响工作，向用户说明证据与阻碍。没有合适替代模型时可以直接报告用户。有明确进展的正常工作可以继续。

改变已确认的设计或验收条件，仍然需要用户参与决定。

## 官方技能与特殊代理机制

保留 Anthropic 官方审查流程及其模型与审查方法的配合关系。

- 普通 Agent 可以通过 `agent.spawn` 指定独立模型。
- 技能的 `context: fork` 使用独立上下文；其外层启动可以绕过 `agent.spawn`。
- `Agent(subagent_type="fork")` 复制完整主对话，启动时忽略模型覆盖参数。
- Workflow 的代理启动事件存在内容不可改写的约束。

本机 Claude Code 2.1.319 的 `/code-review` 使用技能独立上下文，官方说明的目的是让审查在后台进行，避免占满主对话。审查指令根据模型族与 effort 选择。实际请求模型与这些指令必须保持匹配。

`turn.step` 的公开契约允许改写请求模型及 effort，但本次没有运行审查或验证跨模型切换。模型路由需要按各类入口的实际契约接入。

## 个人使用证据与路由校准

持续收集正常任务的选择依据、验收结果、返工原因、自然反馈，以及可获得的耗时和消耗数据。用户反馈保留原话和对应任务，校准时由用户确认其含义。

偶尔邀请用户评价已完成任务或长期任务中明确交付的成果。评分可跳过，普通执行步骤不反复请求评价。评分采用一到五分，每天最多邀请一次，具体方式见[实现方案](model-routing-implementation.md)第 9 节。

评分评价用户收到的成果。多个模型共同参与时，结合具体意见及各部分的验证结果判断原因；整体评分不能直接作为所有参与模型的能力评价。未收到评价的任务不自动记为用户满意。

每两周检查一次记录。已有具体任务证据能够支持一项调整讨论时（两周内同一条规则至少 3 个任务出现同类问题，条件见实现方案第 9 节），通过 Telegram 提醒用户并展示相关案例；证据不足时继续积累。用户可以随时主动发起校准。

校准需要解释个人使用分布、观察到的模型表现、证据限制以及路由表调整建议。用户参与决定调整内容，确认后生效。额外模型对比实验的执行范围尚未授权。

## 已核实的实现基础

- JEV 已按主循环与子代理分别判断任务类型及深入推理需求，并设置 effort；当前钩子没有据此选择模型。
- Magpie 的当前目录包含 Claude 与 Codex 模型。
- Telegram Router 已实现任务派发及追问转交，任务子代理模型固定为 `opus`。
- Telegram 的任务映射在最后活动十四天后清理。原子代理无法接收消息时，接手输入由原始请求和最新追问组成；这不足以保证长期任务关键细节完整恢复。
- JEV 的现有 outcome 记录包含会话、代理和轮次标识、模型、effort、耗时、输入输出及缓存 token 数量，以及检查结果。它们属于轮次记录，尚不等同于任务验收或原因归属。

原始证据与路径见 `findings.md` 中的 model routing interview 部分。
