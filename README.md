# claude-mods

Personal Claude Code mods (function-hook plugins), one plugin per folder under `mods/`.

| Mod | What it does |
|---|---|
| `subagent-opus` | Under a Fable or Mythos main loop, Agent-tool subagents start on Opus (forks and workflow agents untouched). |
| `no-bg-poll` | Denies `sleep N && <reader>` polling; background tasks notify on completion. |
| `workflow-opus-guard` | Under a Fable or Mythos main loop, denies a Workflow script unless every `agent()` call pins `model: 'opus'`. |
| `advisor-guard` | Under a Fable or Mythos main loop, replaces the `advisor_tool` reminder and any advisor section of the system prompt with Claude Code's own `Never consult the advisor tool.`, so the session does not pay for a second premium model. The advisor runs server-side, so no hook can refuse a call or drop the tool; a person who asks for it by name can still get it. Subagents are left alone. |
| `mode` | `/mode academic\|general` writes the repo's `.claude/settings.local.json` (restart to apply); paper repos get a one-time hint; status line shows academic mode. Both modes reply in the Plain output style; academic mode adds `prompts/academic.md` (academic judgment, submission register, review and rebuttal rules, the `~/.agents/writing/LESSONS.md` reminder) to the system prompt. |
| `jev` | Sets each Opus, Mythos, GPT-6 Astra or GPT-6.1 Sol prompt's effort with Jev (policy.v15). The start level is decided once per prompt from the task kind, read from a table per model (Opus 5.5, default medium; Mythos 5.1 and earlier Opus, default high; GPT-6 Astra with code and prose at medium and research at high; GPT-6.1 Sol with code at medium and explanations, prose, visual work and research at high; both OpenAI models start difficult research at max and accept Magpie provider/model IDs), each kind with a start and a deeper start for work that needs something worked out (OpenAI sources and per-level benchmark numbers in [mods/jev/BENCHMARKS.md](mods/jev/BENCHMARKS.md); Claude sources in `~/.config/jev-opus/eval/effort-sources.md`). The tables start low and raise on failure where a failure shows itself (Opus 5.5: code, operations and visual work low; explanations, prose and research a step higher, since nothing would raise them), and a level a task was raised to holds while Jev reads the next message as carrying on the same task (`followup.v6` asks it beside the fault question); a prompt whose kind Jev is unsure of starts at high. Then, one level above the previous prompt's highest when the prompt says the last turn went wrong (max only after the top level was faulted twice), never below the previous level for a short acknowledgement (`继续`, `ok`), and, with probability `JEV_OPUS_EXPLORE` (default 0.10), one level up or down inside medium..max for exploration on a person's own prompt. Jev reads the conversation as Claude Code holds it, rebuilt from `$.session.messages({ as: 'api' })` at every ask, so it follows Claude Code's compaction: the compaction summary, each message that starts a turn (typed text, a Telegram message's body without its tag, a slash command's expanded body, a background task's summary and result, a message that arrived mid-turn) and each turn's final reply, newest last, as a message array (OpenAI then reads the earlier part from its prompt cache); tool calls and results, intermediate text, reminders, hook context and plugin notes are left out. So 我觉得可以. after the agent offered to write code reads as code, and an approval takes the kind of the work it approves. One request asks the task kind and deep (`task.v6`) and, on a person's message after an agent turn, the fault and same-task questions. A subagent reads its own conversation (its brief, the messages that resumed it, its reports), so a resumed run is decided from the message that resumed it. The level holds for every request of the turn, on every routed model; only the ladder moves it, only up, and only at the next prompt: a check (a Bash command running cargo test/build/clippy/check, pytest, go test/build/vet, tsc, eslint, ruff, mypy, or npm/pnpm/yarn/bun `test` or `run` of a script named test, build, lint, check, typecheck, verify or ci; also inside `ssh` and `docker exec`) that fails again, judged by its exit code alone, after the model changed code, and still fails at the turn's end, starts the next prompt one level up when that prompt continues the work (an acknowledgement, a fault, or a short prompt after an interrupted turn); in a subagent it starts the next run of that subagent (a SendMessage resume) one level above the higher of that run's own level and the level the last run held, and its open checks carry into that run. A code change is a successful Edit, Write, MultiEdit or NotebookEdit, or a Bash command that edits files in place: `sed -i`, `perl -i`, an output redirection or `tee` into a file (a heredoc included), `patch`, `git apply` / `git am`, `git checkout … -- <path>`, `git restore`, or `cp` / `mv` / `install` into the work tree, also behind `sh -c`, `ssh`, `docker exec`, `xargs` and `find -exec`. After exit 0 it counts when a local file it names was modified during the call or is gone after it, and without a look for a remote edit, a patch, `mv`, `cp -p`, or a path with a variable or glob. After a non-zero exit only an edit chained by `&&` into a check counts (`sed -i … && npm test`, where the failure may be the edit's or the check's), and only when every file it names is local and was modified during the call. Such a command is the same check as the check alone, so `npm test` failing and then `sed -i … && npm test` failing is a repeat. What a check writes, and files written from inside an interpreter (`python - <<EOF`, `node -e`), are no code change. A piped run, `|| true`, a denied call, WebFetch, lookups and one-off scripts never count. A background task's report continues the last prompt; a slash command is a new task judged from its expanded text; a Telegram message is a person's prompt. A `/effort` the person runs holds for the session until another `/effort` or a prompt with `[effort auto]`; `/model` is no `/effort`. Other session models (Fable, Haiku) are left alone, prompt included, and so is a subagent whose brief carries the magpie-tasks marker (`[magpie-tasks task=`): its effort is that plugin's, and each of its runs is a `skip` row. The band above the prompt names the model of the loop whose transcript is in view, the main conversation or a subagent opened from the tasks list, and its effort trail (`Mythos 5.1 · ◆ Jev · XHIGH · code`; the model alone, `Fable 5.1`, for a loop Jev leaves alone; `· local routing` without Jev, `· /effort` under a pin, `· done` once a subagent has ended); `/model` renames the main line at once. A prompt may carry its own range, `[effort xhigh..max]`, `[effort >=xhigh]` or `[effort max]`: that prompt's start and raises stay inside it, and the next prompt returns to the configured range (`/effort` pins still win); a subagent started under that prompt inherits the range unless its brief carries a tag of its own, whatever model the main loop runs; the journal records it as `promptBounds` (`promptBoundsInherited` on a subagent). Reads `~/.config/jev-opus/.env` (`JEV_OPUS_CONFIG_DIR` overrides the folder); journal rows (`prompt`, `step`, `check`, `outcome` with tokens, wait, checks and raises per turn, `skip`) are appended to `mod-journal-YYYY-MM-DD.jsonl` (UTC) there; each decision Jev made records `jevUsage` (messages, input tokens, tokens OpenAI read from its cache). Jev is OpenAI's Decisions API (`https://api.openai.com/v1/decisions`, `JEV_MODEL`, default `gpt-6-luna`), keyed by the file `JEV_API_KEY_FILE` names (`~/` is the home folder, a relative path the config folder; it wins over `JEV_API_KEY`) or by `JEV_API_KEY`, within `JEV_DEADLINE_MS` (default 10000: 8.3 s was measured for an 861K-token conversation). Without a key, heuristics only. When the ask fails (deadline, an HTTP error such as a 429 rate limit, no valid answers, circuit open) or the key file cannot be read, the turn starts from the heuristics and the row's `jevError` says why (`deadline`, `http-429`, `key-file`, …). |
| `reply-language` | Attaches one line naming the reply language from the `language` setting (`chinese` → `用中文回复用户。代码、命令、标识符和提交信息保持原样。`; any other value → `Reply to the user in <language>. …`) beside every prompt: a person's own, a Telegram message, a background task's notification, a slash command. The system prompt's language rule sits at the far end of a long session, and English right before a reply (task notifications, compaction summaries, subagent reports) pulls the reply into English; the line sits next to the reply. No `language` setting, no line. |
| `tg-router` | Makes the Telegram session (`examples/claude-telegram`) a Router: `dispatch` hands each request to a background Opus worker and posts a one-sentence ack under it; a Telegram reply to any message of a request goes straight to that request's worker (`$.session.send`, by the worker's name `tg-<chat_id>-<message_id>`), never through the Router; a message that replies to nothing but continues an open task goes there through the Router's `forward` tool (the Router context lists each open task with its worker name; the host posts a one-line note under the message; when the message could belong to several tasks the Router asks which); each worker run's answer is posted under the message that started it, and a run of 30 s gets a progress card (a Router turn's shows its tool count and current tool by description or file name, redacted; a worker's shows elapsed time only, since the host runs no `tool.call` hook of the mod that spawned a subagent for that subagent's calls); a worker hands an unrelated follow-up back with a `HANDBACK <message_id>: <reason>` line in its answer, which the mod strips and resubmits to the Router. The main loop may only dispatch, use the channel's tools, `TaskStop`, `ToolSearch`, `SendMessage` and herdr/tmux commands. Tasks live in the mod's store for 14 days after their last message. A message typed in the session's own terminal (or through Remote Control) is dispatched the same way (chat_id `tui`, worker `tui-<id>`), and its worker's answer comes back to the terminal as a message from the plugin. Not in the marketplace: the launcher loads it with `--plugin-dir`. |
| `html-plan` | The community `html-plan` skill (anthropics/claude-plugins-community, html-plan 1.0.0) with Chinese prose: `pack.mjs` reads `。？！` as sentence ends and counts two CJK characters as one word, and under `<html lang="zh">` the page buttons, badges and the copied response are Chinese. Upstream changes: re-copy `skills/` and re-run the edits listed in `mods/html-plan/CHANGES.md`. |
| `math-render` | Draws the TeX math in assistant replies as Unicode in the terminal; the stored message and what the model reads keep the TeX. Inline math (`$…$`, `\(…\)`) becomes one line (`∑ᵢ₌₁ⁿ xᵢ²`, `(a + b)/2`, a script with no Unicode form written `x^q`); display math (`$$…$$`, `\[…\]`, a bare `equation`/`align` environment) on its own line becomes a fenced block of character art: stacked fractions, limits above and below, integrals and brackets stretched to their content, matrices, `cases`, `aligned`. Code spans, fenced code, prices (`$5 or $10`) and a display block still streaming stay as written; display art wider than the reply, or inside a table row, is written on one line. Characters only: the terminal draws no formula images here. |
| `context-memory` | The working model keeps a task note with `notes_write` (a short system-prompt section says when). At compaction the mod saves the conversation in local SQLite, adds the latest note to the native summarizer's instructions, keeps every message the native compaction returns and appends one plain-text handoff carrying the note verbatim and the archive references; `history_search` / `history_read` retrieve the original text of the current branch (a subagent also reaches its session's main conversation) or, with `scope: project`, of the project's other sessions, which `history_sessions` lists; the archive expires with Claude Code's own transcripts. The mod makes no model requests of its own. See [usage and verification](mods/context-memory/README.md). |
| `magpie-tasks` | Only in interactive `claude-magpie` sessions (the Magpie gateway): each new window becomes a long task. Jev recommends an architect model (Opus 5.5, Astra or Sol 6.1), the person confirms it, and the architect runs as a background session that stays in the project main directory and may write only `.planning/findings.md`, `CONTEXT.md` and `.planning/plan-*.md`/`.planning/*.html`; implementation goes to subagents in a Git worktree of the project, and its `integrate` tool applies their changes to the working tree (nothing is committed). Every subagent the architect or the Telegram Router starts is routed by `rules/routing-rules.json` (19 rules from the model routing table): Jev picks the rule and whether the task needs deeper reasoning, the plugin sets the model and the effort of each step, an explicit model needs a `[model-reason …]` line, and the brief carries a `[magpie-tasks task=…]` marker that JEV skips. Telegram daily tasks get an acceptance subagent, integration into the project, diagnosis and one model change per blocker; startup recovery resumes stopped architects. Records are under `~/.config/magpie-tasks`. Must be installed after `jev` and `subagent-opus`. See [mods/magpie-tasks/README.md](mods/magpie-tasks/README.md). |

## Examples

- [`examples/claude-telegram`](examples/claude-telegram): one resident Claude driven from a Telegram chat as a Router with background workers (`tg-router`), and `tg-channel`, the official channel server that also reports which message a message replies to; launcher script and setup.

## Install (this machine)

```
claude plugin marketplace add ~/sipeng/claude-mods
claude plugin install <mod>@sipeng-mods --scope user
```

The marketplace is a local folder, so sessions read each mod straight from `mods/<mod>`:
edit, then `/reload-plugins`.

Install order matters where two mods set the same field: `claude plugin install` appends the new mod at the end of `enabledPlugins`, which makes it the innermost, and the innermost decides. Install `magpie-tasks` after `jev` and `subagent-opus`; installed before them it shows an error at session start and stays off.

## Check

```
claude plugin validate mods/<mod>
claude plugin test mods/<mod>
```

Jev's start levels are scored offline against the journal: `extract` joins each prompt row with its text from the session transcripts, `sheet` adds unlabeled prompts to the label file, `score` replays the current policy against the labels (person and `claude-draft` labels reported apart) and tabulates outcomes by start level. Items and labels hold your own prompts and stay in `~/.config/jev-opus/eval/`.

```
bun mods/jev/eval/jev-eval.ts extract
bun mods/jev/eval/jev-eval.ts sheet
bun mods/jev/eval/jev-eval.ts score
```

Labels are reviewed in the browser at `https://cc.bbd.sh/label/` (same login as `/plan/`): `mods/jev/eval/review-server.ts` runs as the user service `jev-label` on `127.0.0.1:7241`, shows each prompt without Jev's own decision, and saves a confirmed row as the reviewer's label (`JEV_REVIEWER`, default `sipeng`).
